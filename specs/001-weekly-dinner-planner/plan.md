# Implementation Plan: Weekly Dinner Planner

**Branch**: `001-weekly-dinner-planner` | **Date**: 2026-07-18 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-weekly-dinner-planner/spec.md`

## Summary

A single-user, conversational meal-planning agent delivered as a **Telegram bot**. The
conversation and meal curation are driven by the Claude API (Claude Sonnet 5 with
adaptive thinking and the server-side web-search tool for recipe sourcing); all hard rules are enforced by deterministic Python code. The
core pattern is **"the model
proposes, the code disposes"**: the agent converses freely and curates meals, but every
draft plan must pass through a strict-schema `propose_plan` tool whose payload is
validated by deterministic validators (meal counts, exactly-one batch/stretch flags,
4-week repetition window, budget math). Grocery-list merging and the estimated weekly
bill are computed deterministically from the plan's structured ingredients — never
free-generated by the model — which makes SC-002/SC-003 testable. Accepted plans and
next-session cooked check-ins persist in SQLite; abandoned sessions leave no trace.

## Technical Context

**Language/Version**: Python 3.12+

**Primary Dependencies**:
- `anthropic` (Claude API SDK — beta tool runner, server web-search tool, streaming, prompt caching)
- `python-telegram-bot` v22 (async Telegram Bot API framework, long polling)
- `pydantic` v2 (domain models + plan payload validation)
- Dev: `pytest`, `pytest-asyncio`, `ruff` (lint + format), `mypy` (type checking)

**Storage**: SQLite (stdlib `sqlite3`), single database file; stores accepted weekly
plans, per-meal history rows with cooked status, and generated artifacts. In-flight
session state (staged draft plan, session config) is in-memory only, so abandoned
sessions are never persisted (FR-021).

**Testing**: pytest. Integration tests drive the real conversation/tool loop against a
scripted **fake LLM transport** (deterministic, offline); contract tests pin the tool
schemas and the WeeklyPlan JSON schema; unit tests cover grocery merging, repetition
rules, validators, and bill math. Live-API smoke tests exist but are marked and
excluded from the default suite (constitution II: deterministic, no network).

**Target Platform**: Any always-on Linux/macOS machine (home server, Raspberry Pi,
small VPS). Telegram long polling means **no inbound network exposure** is required.

**Project Type**: Single project — one long-running bot process.

**Performance Goals**: Per spec SC-007 — visible response (typing indicator/ack) to any
message within 5 s; complete draft plan within 30 s of receiving dinner+lunch counts.
Non-LLM operations (history queries, grocery merge, validation) adopt the constitution
defaults: < 200 ms p95.

**Constraints**: Single user (one Telegram chat ID allowlisted); artifacts must be
deterministic given a plan; one plan per week, editable until week end; no pre-loaded
recipe database; phone-readable message formatting (Telegram MarkdownV2).

**Scale/Scope**: 1 user, 1 plan/week (~52 plans/year), 3–4 meals/plan, 5 agent tools,
history retained indefinitely (trivially small data).

## Architecture Overview

```
Telegram  ⇄  bot/ (python-telegram-bot)          transport: messages in/out, typing
                 │                                indicator, chat-ID allowlist, formatting
                 ▼
             agent/ (Claude conversation loop)    system prompt (cached), tool runner,
                 │            │                   server web_search tool
     client tools│            │server tool
                 ▼            ▼
             services/     Anthropic web search   deterministic logic: plan validation,
                 │                                grocery merge, bill math, repetition
                 ▼                                window, history queries, check-in
             SQLite                               accepted plans + meal history
```

Agent tools (full contracts in [contracts/agent-tools.md](./contracts/agent-tools.md)):

| Tool | Kind | Purpose |
|---|---|---|
| `get_meal_history` | client | Past weeks' meals, cooked status, techniques used (FR-023/024) |
| `record_cooked_checkin` | client | Persist previous week's cooked/skipped statuses (FR-021) |
| `propose_plan` | client, `strict: true` | Validate + stage a structured draft plan; returns validation errors or computed grocery/bill preview (FR-004–009, FR-018) |
| `accept_plan` | client | Persist the staged draft as the week's plan; returns final grocery list + bill (FR-011–015, FR-021/022) |
| `web_search` | server (`web_search_20260209`) | Recipe sourcing with citations (FR-010) |

Post-acceptance edits (swap, serving change) re-enter through `propose_plan` →
`accept_plan`, which upserts the same week's plan and regenerates artifacts (FR-015,
FR-022).

All technology decisions and rejected alternatives: [research.md](./research.md).

- [x] **UX consistency gate (Principle III)**: Surface is a text-message bot, so the
  constitution's visual-UI provisions apply as far as the platform allows (per spec
  assumption). Loading state = immediate typing indicator + ack message (FR-027);
  empty states = first-ever session (no history → no check-in, no repetition rule) and
  zero-lunch weeks, both specified in the spec; error states = FR-028 (name the failed
  constraint + next step, never empty output). Canonical terminology fixed in
  [data-model.md](./data-model.md): "plan", "meal", "batch meal", "stretch meal",
  "grocery list", "estimated bill" — one term per concept in all user-facing text.
  WCAG interactive-feedback intent is met by the 5 s visible-response budget;
  screen-reader/contrast provisions do not apply to a chat surface the product does
  not render.
- [x] **Performance gate (Principle IV)**: Spec provides measurable numbers (SC-001,
  SC-007); constitution defaults (< 200 ms p95) explicitly adopted for all non-LLM
  code paths in Technical Context. SC-007 gets an automated check: integration test
  asserts the ack is emitted before the agent call begins.

**Structure Decision**: Single project (`src/sous_chef/` + `tests/`). One process hosts
both the Telegram transport and the agent loop; there is exactly one user, so no
service split, queue, or web tier is justified. The four packages separate the only
boundaries that matter for testing: transport (`bot`), LLM orchestration (`agent`),
deterministic business logic (`services`), and typed data (`models`).
